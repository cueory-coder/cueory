# Technical decisions

One line each, newest at the bottom. Reasons are kept short on purpose.

- **D-01** Node 24 LTS, pinned in `.node-version`. It has long-term support and both CI and Cloudflare read this file.
- **D-02** TypeScript 6, not 7. Astro's type checker (`@astrojs/check`) supports only up to 6.
- **D-03** Tailwind v4 with `@theme` in `src/styles/tokens.css`. The default palette is removed so only tokens can
  be used.
- **D-04** (Replaced by D-19.) Starter fonts were Newsreader and Atkinson Hyperlegible Next.
- **D-05** (Replaced by D-38.) Cloudflare **Pages**, not Workers. Cloudflare's docs tell new projects to start on Workers, but Workers
  builds can only be switched on or off for *all* non-production branches. Pages documents exactly what the brief asks
  for: "Preview branch control → Custom branches = `staging`" (feature branches never use the 500 free builds) and a
  one-click "Enable access policy" lock for previews. The site is plain static files, so moving to Workers later is a
  small change.
- **D-06** Hash-based CSP generated by Astro (`security.csp`). Header-only parts (`frame-ancestors`) are in
  `public/_headers`. CSS is never inlined, so styles stay hash-free.
- **D-07** GitHub repository stays **private** (Christian's decision, 2026-10-31). On a private personal repository,
  CodeQL and GitHub secret scanning need paid GitHub plans, so free substitutes run in CI (D-08, D-18).
  Answer keys and reviewer files still never go in the repository; from Task 2 they live only in Supabase.
- **D-08** Extra secret scan with gitleaks in CI (free, open source), so secrets are caught even while the repository
  is private.
- **D-09** CodeQL workflow skips itself on a private repository instead of failing; it runs as soon as the repository
  is public.
- **D-10** Pages are built as `page.html` files (`build.format: 'file'`), so URLs have no trailing slash.
- **D-11** Unit tests with Vitest. Browser tests with Playwright plus axe accessibility checks at phone and desktop
  sizes.
- **D-12** Newsletter: **Kit** free plan (up to 10,000 subscribers, unlimited sends, unsubscribes handled, double
  opt-in). Alternatives checked: EmailOctopus, Sender and beehiiv cap free plans at 2,500; MailerLite cut its free plan
  to 250 in 2026; Buttondown's free plan is too small. Brevo has unlimited contacts but only about 300 sends a day.
- **D-13** The signup form is plain HTML that posts straight to Kit: no Kit script, no cookies on our pages, and it
  works without JavaScript. The CSP allows posting only to the exact Kit address set in `src/config/site.ts`.
- **D-14** Branch flow: feature branch → pull request into `staging` → locked staging site → pull request into `main`.
  The repository starts with one empty commit on `main` and `staging`, so even Task 1 arrives through a pull request.
- **D-15** The staging site lives at `staging.cueory.pages.dev` (Cloudflare's branch address), which the one-click
  preview lock covers. No `staging.cueory.app` address, so there's no second lock to manage.
- **D-16** Supabase keep-alive and backup jobs moved to Task 2, together with the Supabase projects they serve.
- **D-17** Dependabot security alerts on; Dependabot automatic security-fix pull requests off, because GitHub opens
  them against the default branch (`main`) and they would skip staging. Weekly version updates target `staging`.
- **D-18** Code scanning while private: Semgrep Community Edition in CI (free, no account, usage reporting off) with
  the JavaScript, TypeScript, React, GitHub Actions and secrets rule sets. The build fails on any finding.
- **D-19** Brand guide adopted (`docs/BRAND.md`): exact Daytime and Evening palettes, Inter self-hosted for all text,
  automatic dark mode from the device setting. Buttons are Espresso (day) or Evening Ivory (evening); hover uses
  Bronze or Sand. Mocha and Bronze-on-charcoal are fill-only because they fail text contrast.
- **D-20** (Replaced by D-22.) A stand-in wordmark was generated from Bodoni Moda Medium.
- **D-21** Favicon is the square Evening logo (charcoal with Evening Ivory), following the guide's 1:1 primary format.
- **D-22** Logo = vector traced from Christian's banner (potrace 2.1.8 via sharp 0.35.5, run outside the project; 4×
  upscale, threshold 170 as in the spec). The traced paths are stored as one geometry master in `brand-source/`, and
  every logo file is built from it, so light and dark can never drift apart.
- **D-24** Christian approved the traced logo on 2026-10-31. It is frozen as geometry master v1.0, and a test pins its
  checksum. Brand files need Christian's review (CODEOWNERS).
- **D-23** Colors follow the spec's website table: dark-mode buttons are Sand (not Evening Ivory), and form borders and
  focus outlines are Bronze (day) / Sand (evening). Headings stay Inter, as the brand board says. The spec's
  Bodoni Moda heading idea is marked there as a proposal only.
- **D-25** Theme switch: a Light / Dark / Follow device radio group in the footer of every page, Follow device by
  default. A pick sets `data-theme` on the page and is kept in the browser's local storage (never sent to us). A tiny
  inline `<head>` script applies the saved pick before the page paints; Astro doesn't hash hand-written inline scripts,
  so `astro.config.mjs` adds that script's exact hash to the CSP, and a build test checks every inline script is allowed.
  Without JavaScript the switch stays hidden and the device setting decides.
- **D-26** Batch checker (Task 3): `npm run check-batch -- <folder>`, a TypeScript script run straight by Node 24
  (type stripping, no extra dependency), with its own strict CSV reader so a malformed file stops the check instead of
  being half-read. Format and pass rule in `docs/BATCHES.md`: a question passes only if every reviewer (at least five)
  matches the key and marks it pass, and every mechanical check passes. Answer balance is a warning, not a failure.
  Links are checked offline by default; `--check-links` asks the websites and is never run in CI. Real batches stay
  under `content/batches/`, which git ignores, so answer keys and reviewer results never reach the repository (D-07).
- **D-27** The lesson stepper renders only in the browser (`client:only`), so without JavaScript the page shows just
  the full lesson list, with no duplicate first sentence and no dead buttons. Codex review of PR #1.
- **D-28** Components may not use Tailwind "arbitrary values" (`text-[3.5rem]` and the like); every size, spacing and
  letter-spacing value is a named token. A unit test scans `src/` for them. Codex review of PR #1.
- **D-31** (Buttons and saving updated by D-37.) Cards mode (Task 4): decks are JSON files in `content/cards/`, one per lesson, checked by the build. One card
  at a time with real buttons ("Show answer", "Got it", "See again", "Back"); "See again" puts the card at the end of
  the round. No flip animation, so there's nothing to turn off for reduced motion. Progress isn't saved yet; that comes
  with guest progress later in Task 4.
- **D-29** When the batch checker can't read a batch, it deletes the earlier `passed.csv` and `failed.csv` and writes a
  "not checked" `report.md`, so a stale approval can't be mistaken for a current one. Codex review of PR #2.

  gpt2, gpt3, gemini, claude_sonnet, codex, claude_final, christian), so a typo is a batch problem (exit 2) instead of
  silently counting; at least five files, none individually required. The pass rule stays unanimous. A `pending`
  verdict is its own status: an item with nothing wrong except pending reviews goes to `pending.csv`, never passes,
  and the exit code is 1 (0 only when every item passed). Items are single-answer only; select-all-that-apply waits
  for Christian's content decision. Answer balance unchanged.

- **D-39** (Which paths wait for Christian before launch: D-42.) Staging auto-merge (Christian's plan: "a bot merges non-sensitive pull requests once Codex calls them

  Merges made by the workflow don't start CI on `staging` (GitHub doesn't start workflows from its own token's
  pushes); each pull request's CI already tested it merged with `staging`. Reason: Christian keeps his hands for
  sensitive changes and releases, and clean work reaches the staging site without waiting for him.

- **D-43** Learn mode for card decks (ROADMAP Task 4). Each card climbs three steps: see it (its answer one tap
  away), choose its answer from up to four in the deck (only answers that read differently), then recall it: fill in
  its blank when the deck names one (a card's optional `blank`: words that appear in its back exactly as written,
  checked when the site builds), otherwise type the whole answer. A right choice moves the card up and a right recall
  masters it; a wrong choice stays on that step and a wrong recall goes back to choosing. Anything not mastered comes
  back after two other cards. Typed answers ignore case, accents, punctuation and extra spaces, and "I was right"
  counts a near miss once the student has seen the answer. A deck with only one answer skips the choice step.
  Nothing is saved yet (guest progress is its own Task 4 item); without JavaScript the page points to the cards page.
  The home page's sentence-by-sentence reader is now called "Lesson", so "Learn" only ever means Learn mode
  (Christian's answer on issue #4, 2026-10-31). Reason: Christian's plan for Learn mode, "mixing cards, multiple
  choice, typed answers and fill-in until mastered", starting with card decks, whose answers students can already see
  (D-33).
- **D-44** Matching for card decks (ROADMAP Task 4). A round lays out up to six cards as two lists, terms (fronts) and
  meanings (backs), each in random order; the student picks one from each list in either order. A right pair is
  marked "Matched" in words and with a tick and stays on screen (nothing disappears or moves by itself), and the
  button just used keeps keyboard focus (`aria-disabled`, not `disabled`); a wrong pair counts as a miss and is
  cleared. Picking a second item from the same list moves the pick, and picking the same item again lets go. No two
  cards in a round read the same on either side: a card that repeats another's term or meaning waits for a later
  round, so a pair is right only when both halves come from the same card and every round can be finished (Codex
  review of PR #18). Bigger decks play six pairs a round in deck order. Every item is a button, so there is no
  dragging, and there is no timer. Nothing is saved yet; without JavaScript the page points to the cards page.
  Reason: the home page promises "Pair terms with what they mean", and the card decks already hold the pairs.
- **D-45** Select-all-that-apply questions in batches (Christian's decision, 2026-10-31: yes, scored all-or-nothing,

- **D-49** Site search in the ☰ panel (Christian's change request, 2026-10-31). Pagefind 1.5.2 (MIT, pinned) runs
  after `astro build` (`pagefind --site dist`) and writes a static index to `dist/pagefind/`; nothing is sent to anyone
  else. It indexes only each page's `<main>`, never the menus, notice or footer, and leaves out pages kept out of search
  engines (404, the signup thank-you page). Results take each page's own title ("home" for the home page). The index
  loads the first time the field is used, never with the page, and runs on the page itself (`noWorker`), so no `blob:`
  worker is needed. Results are built as text: the matched words are bold, and no HTML from the index reaches the
  page. Arrow keys move between the field and the results, and an empty search says "no results" plainly. Pagefind
  searches with WebAssembly, so `script-src` gains `'wasm-unsafe-eval'`: it allows compiling WebAssembly, never
  running JavaScript strings, and scripts still come only from this site (a build test checks there is no other
  `unsafe-eval`). Reason: Christian asked for real search with Pagefind; a static, self-hosted index keeps the site
  free and private, and without `'wasm-unsafe-eval'` the search fails in every browser.
