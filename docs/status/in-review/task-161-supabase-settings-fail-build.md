status: Task 161, bad public Supabase settings stop the build (security audit item 2): a small Astro integration (`src/islands/supabasebuildcheck.ts`, registered in `astro.config.mjs`, outside the CSP block) runs the `supabaseenv.ts` checks in the `astro:config:setup` hook, before anything is bundled. Both unset builds with accounts off; only one set, a wrong address, a secret key (`sb_secret_`), a legacy JWT (`eyJ`) or anything that isn't a publishable key stops `astro build` with a reason that never prints the value (`astro dev` only warns). Tests use fake canaries built at run time, including one that loads the real `astro.config.mjs`. Why the config: Astro's environment-variables guide (https://docs.astro.build/en/guides/environment-variables/), as the Task 153 audit cites it, says `PUBLIC_` settings are compiled into client assets, and the config already reads them with Vite's `loadEnv`, so an integration hook there is the earliest point with the values in hand. Astro's `env.schema` (`envField`, per Astro's own config types) validates each variable on its own, so it can't express "both or neither", and moving to it would change the sign-in client. The guide page could not be fetched in this session (the fetch was not approved), so the lead should open that link before the PR goes up.
decision: D-pending (Task 161) A malformed or secret-shaped `PUBLIC_SUPABASE_*` setting fails the build instead of quietly turning accounts off; leaving both unset is still allowed. Reason: a secret or a wrong address must never be bundled into the public site.
